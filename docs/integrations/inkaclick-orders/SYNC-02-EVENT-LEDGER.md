# SYNC-02 — Event ledger contract

SYNC-02 creates the transport-neutral audit envelope that later synchronization units will use. It does **not** synchronize any business domain yet.

## Canonical identity

The only business order identifier is the WACRM UUID:

`canonical_order_id = public.order_confirmations.id`

InkaClick's internal `confirmed_orders.id` remains legacy/local and is deliberately absent from the event contract.

## Event identity and idempotency

Every event carries:

- `canonical_order_id`
- `origin_system`: `wacrm` or `inkaclick`
- `origin_event_id`: stable UUID generated by the origin
- `event_type`: namespaced value such as `payment.confirmed`
- `event_version`
- `idempotency_key`
- `occurred_at`
- `payload`

The database has unique keys on both `(origin_system, origin_event_id)` and `(origin_system, idempotency_key)`. An exact replay returns the existing event; a replay with changed identity/content fails closed as `sync_event_identity_conflict`.

## Anti-loop rule

Imported events always preserve their original `origin_system`.

On WACRM, future outbound workers are allowed to read only `order_sync_outbound_events`, whose predicate is:

`origin_system = 'wacrm'`

Therefore an event imported from InkaClick is never eligible to be emitted again as a WACRM-origin event.

## Receipts

`order_sync_receipts` tracks the consumer-side lifecycle independently from the immutable event:

`pending -> processing -> applied | ignored | conflict | dead_letter`

SYNC-02 only creates idempotent pending receipts. Claiming, delivery and state transitions belong to the later transport/worker unit.

## Safety

This migration is additive. It creates no triggers on orders, payments, vouchers, logistics, shipments or messages; it sends no HTTP requests and activates no cron or flag.
